# ADR 002: 초기 소규모 수집·검증은 notebook으로 실행

## 상태 (Status)

수락됨

결정일: 2026-09-12.

## 배경 (Context)

Core-4 수집 초기에는 소스별 응답 형식과 데이터 정의를 확인하고 중간 변환 결과를 살펴봐야 한다. 이 탐색 단계에서 CLI·패키지 구조를 먼저 완성하면 실제 응답을 이해하기 전에 구현 범위가 커질 수 있다. 기존 notebook 4개에는 과거 모델·전처리와 저장 결과가 있어 새 수집 실험과 분리할 필요가 있다.

## 결정 (Decision)

초기 소규모 수집·응답 검사·정규화 검증은 새 Jupyter notebook을 실행 진입점으로 사용한다. 실행 환경은 ADR-001의 프로젝트 `.venv`와 CPython 3.14를 따른다. CLI·패키지 구현을 선행 조건으로 두지 않는다.

기존 notebook 4개는 원래의 데이터 처리·모델 역할 구분을 유지해 별도 보관한다. 내용·저장 출력·메타데이터를 보존하고 새 수집 코드를 보관본에 섞지 않는다.

반복 사용이 확인된 로직은 이후 공통 패키지로 추출할 수 있다. 정기 실행·CLI 도입은 반복 배치 요구가 생기는 시점에 별도로 검토한다.

## 결과 (Consequences)

### 긍정적

#### 응답과 중간 변환을 단계별로 확인하기 쉽다

소량 데이터를 직접 살펴보며 소스 정의와 품질 문제를 확인할 수 있다. 기존 notebook 중심 작업 방식과도 연결된다.

#### 과거 연구와 새 수집 실험의 경계가 명확해진다

보관본을 유지하면서 새 코드를 작성하므로 이전 결과를 비교 자료로 활용하기 쉽다.

### 부정적

#### 셀 실행 순서와 숨은 상태에 영향을 받는다

부분 실행만으로는 재현성을 판단하기 어렵다. kernel을 재시작한 뒤 전체 순서 실행으로 확인해야 한다.

#### 반복 실행과 자동화에는 추가 정리가 필요하다

탐색 코드가 중복되거나 배치 요구가 늘면 공통 로직 추출과 별도 실행 진입점이 필요해진다.

### 중립적

#### 초기 탐색 단계에 적용한다

운영 단계의 실행 방식을 notebook으로 고정하는 결정은 아니다. 모델·전처리·원자료 내용 변경도 포함하지 않는다.

#### 데이터·인증 정책은 별도로 유지한다

notebook 사용이 소스·좌표·단위·가용성·평가 정책을 확정하지 않는다. 비밀값은 환경변수로 읽고 출력·로그에 남기지 않으며, 의존성은 notebook 밖에서 관리한다.

## 검토한 대안 (Options)

### 대안 1: CLI·패키지부터 구현

재사용과 자동 실행에는 적합하지만 현재의 소량 탐색에 필요한 응답 확인보다 구조 설계가 앞선다. 초기 단계의 선행 조건으로 채택하지 않았다.

### 대안 2: 레거시 notebook 직접 개조

기존 코드를 활용할 수 있으나 과거 실험 결과와 새 수집·검증 과정이 섞인다. 비교 기준을 보존하기 위해 별도 notebook을 선택했다.
