# 설계 노트

커피 가격을 예측하는 것도 중요하지만, 이번에는 데이터를 받는 데서 끝내지 않고 결과를 보여주는 데까지 연결해보려고 한다. 우선 혼자 돌려볼 수 있는 크기로 시작한다.

## Parquet에 저장하고, 필요하면 DuckDB로 읽기

10년치라고 해도 일별 데이터라 커피 가격은 2,519행이다. 지금부터 DB 서버를 따로 관리할 필요는 크지 않다. 수집한 표는 Parquet에 저장하고, 날짜나 숫자 타입도 그대로 넘기는 쪽을 골랐다.

여러 파일을 SQL로 묶어 보고 싶을 때는 DuckDB를 쓴다. [Parquet를 바로 조회할 수 있어서](https://duckdb.org/docs/current/data/parquet/overview) 데이터를 다시 DB에 넣는 단계가 필요 없다. 현재 수집기는 pandas로 저장까지 처리한다. 서비스에서 동시 조회나 예측 이력 관리가 필요해지면 그때 PostgreSQL을 검토할 생각이다.

## 확인은 notebook, 반복 수집은 스크립트

처음에는 응답 모양과 결측치를 한 셀씩 볼 수 있어서 notebook으로 시작했다. 반복해서 데이터를 받는 부분은 이제 `02_backfill_10y.py` 하나로 뺐다. notebook은 저장된 파일럿 자료를 읽고 표와 그래프를 확인하는 용도로 남겼다. 필요할 때만 같은 스크립트로 작은 구간을 다시 받는다.

환경은 기존 Apple Silicon Mac의 Python 3.14 `.venv`를 그대로 쓴다. Colab의 Drive 경로나 셀 안의 패키지 설치는 새 코드에 넣지 않았다.

## 첫 모델은 Close부터

Yahoo `KC=F`의 Close를 커피 가격 기준으로 쓴다. High–Low 범위를 벗어난 행이 있지만, 원인이 확실하지 않은 값을 잘라내거나 보간하면 학습할 시계열 자체가 바뀐다. 값은 남기고, 첫 모델은 과거 Close로 만든 피처부터 비교하기로 했다. 자세한 과정은 [트러블슈팅](troubleshooting.md)에 정리했다.

타깃은 5거래일 뒤의 `ln(Close[t+5] / Close[t])`. 거래일 누락을 확인한 뒤 만들고, 결측 가격으로 정답을 만들어내지는 않는다. 로그수익률에도 계약 연결 시점의 가격 차이는 남을 수 있다.

평가는 시간 순서로 나눈다. 학습 데이터의 5일 뒤 정답이 검증 구간에 걸치지 않도록 경계도 비워둔다. 학부 notebook에서는 테스트 입력의 스케일 처리와 평가 구간 사용에 혼선이 있었으므로, 예전 지표를 새 모델의 성능으로 가져오지는 않는다. 2016~2023년 개발, 2024~2025년 평가를 후보로 두되 이미 본 기간인지 확인한다.

거시·기상·COT는 수집해 두고 나중에 하나씩 더해본다. 관측일과 발표일이 다를 수 있어 가격 날짜에 바로 붙이지 않는다. 서비스 예측 시점은 기존 UTC 23:00 기준을 유지하고, 그날 가격을 못 받으면 예측을 건너뛴다.
